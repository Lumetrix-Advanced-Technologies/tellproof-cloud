## 2026-10-16 · P4-6 · JWKS and key rotation

**Built.** Key validity in all three verifiers: `internal/pack` (`ParseJWKS` returns a `KeySet` with `nbf`, `exp` and revocations; `Verify` applies `Vouches`; `KeySetOf` for raw keys), `web/verify/verify.js` (`importJWKS`, `issuedAtSeconds`, `keyVouches`, `key_status` and page wording) and `concierge/verify.py` (JWKS input, same rule, exit 2 for a malformed key file). New vectors `spec/vectors/key-manifest.json` with `keys/` from `make_key_vectors.py`, run by Go, Node and Python (`make vectors`). Server: migration `0003_signing_keys.sql`, `internal/keys`, `GET /.well-known/jwks.json`, `plumbline-server keys`, and the issuer's `CheckSigner`. Choices in D-042.

**Problems.** The new vectors caught a real divergence between verifiers: Go's `json.Number` happily decodes the JSON string `"1786489200"`, which JavaScript and Python refuse, so Go would have accepted a key set the others reject. NumericDates are now raw JSON that must start with a number token. Integers that JavaScript cannot tell apart (`1e9` versus `1000000000`) made me define a NumericDate as "a number with a whole value" in all three, not "an integer literal". Two old Go and JS tests asserted that `revoked` and `nbf` are unknown members; they are now meaningful, so those cases became other unknown members. My first JS test expected fractional seconds from `issuedAtSeconds`; the rule is whole seconds, as Go's `Unix()` gives. The key mix-up test now registers the wrong public key, so it still proves that verify-before-store catches a mismatch even when the registry is wrong.

**Verified.** All fourteen key vectors give the same result in Go, the browser verifier and `verify.py`; the three original manifests still pass unchanged. Through the published JWKS: a pack from the active key verifies; after rotation the old pack still verifies, the old key signing after its retirement is refused (expired), the new key verifies from its `nbf` and is refused one second before it; after revocation the old pack is refused (revoked). The key table refuses every change except setting `exp` once and `revoked_at`/`reason` once, and refuses deletes and truncation. The issuer refuses an unregistered key, signs with a key retired one second after `issued_at`, refuses it at the retirement second, and refuses a revoked key. The endpoint returns 503 with no keys, then a JWKS the Go verifier parses, with the revocation, cache and CORS headers. `plumbline-server keys` adds, refuses a duplicate, retires, requires a reason to revoke, revokes and lists.
