## 2. How to do the routine things

- **Tests**: `make check` needs local Postgres: `docker start plumbline-test-pg` (container name kept from before the rename), then `TELLPROOF_TEST_DATABASE_URL="postgres://postgres:postgres@127.0.0.1:55432/postgres?sslmode=disable" TELLPROOF_REQUIRE_DB=1 GOFLAGS=-p=2 make check`. Then `GOFLAGS=-p=2 make oss-check`.
- **Merging**: PRs into `main` of the private repo with merge commits (stacked branches keep their hashes). If CI is blocked by billing, say so in the PR.
- **Publishing the public repo**: `rm -rf dist/oss && make oss-export && (cd dist/oss && go mod tidy)`, clone the public repo, move its `.git` into `dist/oss`, review `git status`, commit, push. `tools/ossexport` skips caches and `*.egg-info`; check the file list anyway.
- **Release**: update `oss/CHANGELOG.md` (`## vX.Y.Z` is the release notes), export and push, tag `vX.Y.Z` on the public repo. `release.yml` tests, builds, drafts the release and waits for approval of the image job (approve via `gh api .../actions/runs/<id>/pending_deployments` or the UI). Check the draft, publish it; `packages.yml` builds, smoke-tests, attests, then waits for approval: PyPI publishes, npm stages. A founder approves the npm versions on npmjs.com. SDK releases: tag `sdk-vX.Y.Z` when both SDK versions match.
- **npm by hand** (fallback): npm 11.15+, `npm stage publish ./file.tgz --access public` (the `./` matters), approve on npmjs.com. npm rate-limits creating *new* package names; staging was not blocked. A browser approval is good for one request, so a 429 can surface as EOTP.
- **Banner checks**: run the binary under `script -q -c "./tellproof-agent" /dev/null` for a real TTY; `COLUMNS`, `COLORTERM`, `COLORFGBG`, `NO_COLOR`, `TELLPROOF_NO_BANNER` change it.
- **Gotchas**: this machine's `gh` (2.46) has no `gh attestation`; use the attestations API. `ubuntu-latest` moves to Ubuntu 26 from 19 Oct 2026; watch the first runs. Don't leave stray `cat` or heredocs waiting on stdin in long commands.

## 4. Roadmap: how to make it better

Each item: why, what, acceptance. Ordered by value for effort within each area. Propose them to the founders as tasks P8-x in `docs/build-plan.md`.

### 4.1 Ease of setup (time to first dashboard under 2 minutes)

1. **`tellproof-agent init`** (high). One command: detects the project (pyproject, package.json), shows the exact SDK line and where to put it, writes `tellproof.policy.json` from a short Q&A, starts local mode and opens the dashboard. `--yes` for scripts. Acceptance: on the two `examples/` apps, init + one request = a batch visible on the dashboard, with no README reading.
2. **`tellproof-agent doctor`** (high). Checks, with a fix for each: agent reachable from the app (`TELLPROOF_AGENT_URL`), ports free, spans arriving (and how many dropped for content), SDK and agent versions compatible, clock skew, data-dir permissions, policy valid, salt secret present. Acceptance: each failure mode in the troubleshooting table is diagnosed by doctor.
3. **Zero-code instrumentation** (high). `python -m tellproof run app.py` / `TELLPROOF_AUTO=1` with a sitecustomize hook, and `node --import tellproof/register app.js`. Acceptance: the examples report spans with no source change.
4. **More integrations** (high, also distribution). LiteLLM, LangChain/LangGraph, LlamaIndex, Vercel AI SDK, Google Gemini, Azure OpenAI, Mistral, Ollama/vLLM (OpenAI-compatible already works: document it), and an OpenTelemetry Collector exporter. Acceptance: each has a test with a fake client and a README snippet.
5. **Package managers** (medium). Homebrew tap, Scoop/winget manifests, generated by `release.yml`. An install script only if it verifies checksums and attestations; never pipe-to-shell without verification.
6. **Deploy recipes** (medium). Docker Compose with app + agent, a Kubernetes sidecar manifest and a minimal Helm chart, all exercised in CI.
7. **One-click demo** (medium). A devcontainer / Codespaces config that starts `run --local` with the synthetic week (`tools/demolog`, exposed as `tellproof-agent demo`) so visitors see a full dashboard in 60 seconds.

### 4.2 Usability

1. **Shareable reports** (high). `report --html` / `check --html`: one self-contained, signed-digest-stamped page a reviewer can open; `check --markdown` for PR comments; `check --sarif` so failed objectives show in GitHub code scanning.
2. **Dashboard** (high). Objective trends over time, canary miss history, alert thresholds (desktop notification or webhook when an objective turns red), filter by service/environment, CSV export.
3. **Policy authoring** (medium). Publish `spec/policy.schema.json` to SchemaStore so editors autocomplete `tellproof.policy.json`; `policy edit` with guided prompts; `policy explain EO-xxx` printing what the objective measures and how to pass it.
4. **CLI polish** (medium). Shell completions (bash, zsh, fish, PowerShell), `--json` on every command, consistent exit codes documented in one table, errors that end with the command that fixes them.
5. **Canaries** (medium). More probe kinds (system-prompt extraction, tool-call injection, multilingual PII, data exfiltration via markdown links), a probe pack versioned in `spec/canaries.json`, and an agent-side scheduler for apps that cannot run threads.
6. **Coding-agent evidence** (medium). A ready-made GitHub Action (`uses: Lumetrix-Advanced-Technologies/tellproof/ci@v0`) wrapping `ci run/canary/attest`, a PR comment with the verify result, and Claude Code / Copilot hooks that tag agent-authored commits consistently.
7. **Docs** (medium). Turn the 1,200-line README into the website's pages (quick start, each feature, cookbook, troubleshooting) with search; keep the README as the front door.

### 4.3 Security

1. **Harden the workflows** (high, small). Pin every action to a commit SHA (with a comment naming the tag) and add Dependabot for `github-actions`; `persist-credentials: false` on checkouts; keep `permissions: {}` at the top and grant per job (already mostly done); consider `step-security/harden-runner` in audit mode. Acceptance: OpenSSF Scorecard "Pinned-Dependencies" and "Token-Permissions" pass.
2. **OpenSSF Scorecard + badge** (high, small). Add the Scorecard workflow on the public repo and fix what it reports (branch protection on `main` with required reviews and status checks, signed releases, CODEOWNERS). Aim for 8+.
3. **Continuous fuzzing** (medium). Run the existing fuzz targets (OTLP parser, JCS, DSSE) in CI for a few minutes per PR and longer nightly (ClusterFuzzLite), and add targets for the batch decoder, policy parser and pack decoder.
4. **Content-leak regression suite** (high, core promise). A corpus of spans and SDK calls stuffed with secrets, PII and prompts across every provider and attribute spelling; assert nothing of it appears in batches, dry-run output, logs or the dashboard API. Run it in CI for the agent and both SDKs.
5. **Release integrity** (medium). SLSA Build L3 provenance (slsa-github-generator or GitHub's reusable workflow), a reproducible-build check job that rebuilds a release binary and compares digests, and a CycloneDX SBOM of the agent itself attached to each release (the agent already writes AI-BOMs).
6. **Registry hygiene** (small, founders). npm: "require 2FA and disallow tokens" on all eight packages (trusted publishers are stage-only). PyPI: 2FA on all owner accounts; keep trusted publishing as the only path.
7. **Keys at rest** (medium). Optional OS keychain / file-permission checks for the agent's Ed25519 key and salt secret, key rotation for local agents (a signed rotation record in the chain), and `doctor` warnings for world-readable files.
8. **Threat model and audit** (medium). Write `docs/threat-model.md` (STRIDE over SDK → agent → batch → pack → verifier), then commission an independent review of the verifiers and the signing path before the first paying customer.
